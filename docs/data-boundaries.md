# 已知数据边界

历法计算全部来自 tyme4ts，以下边界已在代码中显式处理（见 `src/core/day.ts`、`src/core/month.ts`
与 `src/core/convert.ts`），不会以异常形式抛到界面上：

| 边界                | 行为                                                                                                                       |
| ------------------- | -------------------------------------------------------------------------------------------------------------------------- |
| 公历范围            | 仅支持 **1 – 9999 年**；超出范围的输入被 `isValidDateKey` 拒绝，UI 拦截或返回错误信息                                      |
| 1582 年改历         | **1582-10-05 – 1582-10-14 不存在**，日历会跳过这十天（10月4日直接接10月15日）                                              |
| 月网格越界          | 年首/年末的整周会溢出到 0 年或 10000 年，这些格子渲染为**空白占位**而非报错                                                |
| 法定假日数据        | tyme4ts 内置数据覆盖 **2001-12-29 – 2026-10-10**；超出该区间时 `holiday` 为 `null`，界面不显示「休/班」角标                |
| 年 1、年 2、年 9999 | tyme4ts 的 `getPhase` / `getNineStar` / `getSixtyCycleDay` / `getGods` 等会抛错，这些字段降级为 `null`，其余字段仍正常显示 |
| 藏历                | `RabByungDay` 仅支持 **1950–2050 饶迥年**，超出范围时换算结果里该字段为 `null` 并给出提示                                  |
| 八字排盘            | tyme4ts 无法在 1 年构造时刻，该情况下页面显示「超出历法可推算范围」而不是崩溃                                              |

`DayInfo` 中的 `null` 表示「该字段无法推导」，空数组表示「已推导且确实为空」，两者语义不同。

## 法定假日：内置表 + 在线覆盖层

内置表是**冻结的**（tyme4ts 把它压成一个字符串常量），所以过了 2026-10-10 就再也取不到数据。
`src/core/holiday-overlay.ts` 提供了一个**覆盖层**：逐日期覆盖内置值，覆盖层没有的日期仍
按内置表返回（同一个对象引用，因此离线行为完全不变）。

数据来自 [vsme/chinese-days](https://github.com/vsme/chinese-days)（MIT）：它的 CI 跟随
国务院公告更新，按年发布 `dist/years/<年>.json`，每份含 `holidays`（休）与 `workdays`（班）
两张表。取数在 `src/backend/holidays.ts`（跑在 webview 里，走 `@tauri-apps/plugin-http`），
缓存到 `<数据目录>\holidays\<年>.json`（默认位置是 `%APPDATA%\万年历`，用户可以选择别处，见
[architecture.md](architecture.md) 的「数据位置」），启动时先读缓存再后台更新。

三点要注意：

- **未公布的年份没有文件**（HTTP 404），不是错误。刷新时取今年前后各若干年的窗口，
  404 的年份直接跳过；把「明年还没公布」当成网络故障报给用户是错的。
- **节日名要归一**。来源写「中秋」「端午」「清明」，引擎写「中秋节」「端午节」「清明节」。
  覆盖层是覆盖关系——同一天只要覆盖层有值就用覆盖层的名字——所以 `holiday-overlay.ts`
  里有一张别名表把简称补全，否则会在引擎本来就认识的日子上凭空换一套说法。
- **拉取失败不清空已有数据**。一个过时一年的假日表远比没有表有用，所以失败只报错误码，
  覆盖层保持原状。

这一层的意义在于它修掉了一条会**随时间失效**的边界：内置表的截止日期一到，界面上的
「休/班」角标本该整片消失。

## 用户数据与非用户数据

同一个目录里躺着三类东西，边界划错的地方都出过事：

| 内容                                         | 算不算用户数据       | 依据                                                               |
| -------------------------------------------- | -------------------- | ------------------------------------------------------------------ |
| `settings.json`                              | **算**               | 用户做的决定，没有别处可以还原                                     |
| `holidays\*.json`                            | **算**（虽然可再生） | 离线也能用的那份缓存；搬走时跟着走                                 |
| `updates\*`                                  | **不算**             | 下载产物，随时能重下：搬运时跳过它，不让可再生的东西占搬运的体积   |
| `.tyme-data-dir`                             | 不算数据，算**凭证** | 它证明"这个目录是本应用用过的"，因此旧目录留着它                   |
| `%APPDATA%\com.tyme.desktop\location.json`   | 不在数据目录里       | 它记的就是"数据目录在哪"，存在自己要被搬走的地方等于把钥匙锁在屋里 |
| `%LOCALAPPDATA%\com.tyme.desktop\EBWebView\` | 不算                 | WebView2 自己的缓存与 cookie，应用不持有它                         |

两条由此而来的规则：**启动时不建目录**（还没有用户数据的时候，盘上出现一个空目录不是"准备好
了"，是替用户做了一个他没做的决定），以及**删除只移进回收站**（整份目录一起走，包括那份可再生
的 `updates\`——用户点的是"删掉我的数据"，不是"按上表逐类挑文件"）。U 盘与网络盘上没有回收站
可以退回，那一次就拒绝，不就地销毁。

## 处理方式

边界不是靠 `try/catch` 兜底，而是在 `src/core` 里对每个字段单独降级：

- `buildDayInfo` 对每个可能抛错的字段调用一个 `safe()` 包装，捕获后写 `null`；
- `buildEightChar` 和 `convert` 返回 `{ ok: false, error }`，由 UI 决定怎么呈现；
- 日期键（`YYYY-MM-DD`）在进入引擎之前先过 `isValidDateKey`，越界数据根本不会到达 tyme4ts。

这样做的代价是 core 里有一批显式的边界判断，收益是 UI 层完全不需要防御性判断。
